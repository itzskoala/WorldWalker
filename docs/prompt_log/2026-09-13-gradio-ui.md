## Research done before planning
Read `core/facade.py`, `travel_logic/geocoder.py` + `route_service.py`,
`data/intake.py`, `services/fitbit_service.py`,
`auth_setup/google_health_auth.py`, and `progress/day4.md` (+ its linked
prompt logs). Key findings that shaped the plan:
- `app.py`/`config.py` were genuinely empty - greenfield, matches day4's
  "app.py is still empty - biggest remaining piece" flag.
- `data/intake.py` already has the exact shape/entry point a submit button
  needs (`IntakeRequest` -> `start_journey_from_intake`).
- OAuth already works, but only via `auth_setup/authorize.py`'s manual
  copy-paste-the-code flow (`build_auth_url()` / `exchange_code()`) - no
  HTTP callback route exists.
- Geocoding is Nominatim (free, no key) - `geocode()`/`reverse_geocode()`
  exist; no autocomplete-style search method yet.
- day4 flagged a real, still-open bug: `TravelFacade._sessions` is
  in-memory and per-process - a UI running as a separate process from
  `services/fitbit_service.py`'s webhook would silently not share state.

## Clarifying questions asked (all 4, via AskUserQuestion)
1. **Connect button's OAuth depth** - reuse the manual paste-code flow vs.
   build a real `/oauth/callback` redirect capture. **User picked reuse.**
2. **Where From/To search data source** - live Nominatim search vs. a
   static curated list. **User picked live Nominatim.**
3. **Round trip scope** - UI-only (captured, not acted on) vs. a real
   out-and-back route built now. **User picked UI-only.**
4. **Process architecture** - mount the Gradio UI on the same FastAPI app
   as the webhook vs. a standalone process. **User picked same app** -
   this also fixes the per-process session bug from day4 for free.

## What changed
- `travel_logic/geocoder.py` - `Geocoder.search_places()` (ABC +
  `NominatimGeocoder` impl): autocomplete candidates for the dropdowns.
  Best-effort by design (returns `[]` on a too-short/`None` query or a
  provider error) - callers are a typing UI, not the journey-starting
  `geocode()`, which still raises.
- `core/facade.py` - `TravelFacade.search_places()` (delegates to the
  geocoder) and `current_location_place(lat, lng)` (delegates to
  `reverse_geocode`), both added so app.py only ever talks to the facade,
  never `travel_logic` directly, per the facade's own "single entry point"
  docstring. `start_journey()` gained `round_trip: bool = False`, stored
  on the session but not acted on (see Flagged below).
- `data/intake.py` - `IntakeRequest.round_trip: bool = False`, threaded
  through `start_journey_from_intake`.
- `requirements.txt` - added `gradio`.
- `app.py` (was empty) - the Gradio Blocks UI: trip-type dropdown (Round
  trip/One way), Where From/To dropdowns wired to `search_places()` via
  `.input()` with a 0.3s throttle (Nominatim's usage policy wants light
  volume, not one call per keystroke), a swap button, a "Use current
  location" button (browser geolocation via JS -> `current_location_place`),
  a bright-blue **Connect** button, and a results panel driven by
  `start_journey_from_intake`/`get_map_state`. Dark CSS styled to match
  the Google Flights screenshot.
- `services/fitbit_service.py` - mounts `app.py`'s `demo` via
  `gr.mount_gradio_app`, **after** the webhook route is defined (see bug
  below) - one process, one shared `travel_facade`.
- New tests: `tests/test_geocoder.py` (`search_places`, no network -
  `requests.get` monkeypatched), `tests/test_intake.py`, plus 3 new cases
  in `tests/test_facade.py` (`round_trip` stored but route stays one-way,
  `search_places`/`current_location_place` delegate correctly).

## Real bugs hit and fixed while building this (not hypothetical)
1. **Mounting Gradio at `path="/"` before the webhook route shadowed it
   entirely** - `POST /api/webhook/google-health` started 404ing (caught
   by the existing test suite: 3 failures). Root cause: a Starlette
   `Mount("/")` matches every path under it; routes added to the app
   *after* the mount are never reached. Fixed by moving the
   `gr.mount_gradio_app(...)` call to the end of `fitbit_service.py`,
   after the webhook route - matches Gradio's own documented guidance.
2. **`search_places(None)` crashed** - a Gradio Dropdown fires its
   `.input` event with `None` before any character is typed (on focus).
   `query.strip()` isn't safe against that. Fixed in `search_places`
   itself (`if not query or len(query.strip()) < 2: return []`), covered
   by a dedicated test.
3. **Gradio 6 moved `theme`/`css` off the `Blocks` constructor** onto
   `launch()`/`mount_gradio_app()` - caught via a `UserWarning` on import,
   fixed by hoisting `THEME`/`CUSTOM_CSS` to module constants both entry
   points (standalone `python app.py` and the FastAPI mount) pass in.
4. **A `gr.Button(link=...)` never fires its paired `.click()` handler.**
   First built Connect as a plain button + `.click().then(js=window.open)`
   - real popup blocker silently ate the new tab, since the JS ran after
   a server round-trip, outside the original click's user-gesture window
   (verified live: no second tab appeared). Rebuilt as a real
   `link=/link_target="_blank"` anchor, computed once at import time
   (credentials.json doesn't change per-request) - confirmed against the
   actual Google OAuth consent screen. But `link=` buttons are pure
   anchors with no paired server call, so the "reveal the code-paste box
   on click" idea was dropped too - it's now a plain, always-present
   `gr.Accordion`, simpler and doesn't depend on coordinating two
   different click mechanisms.

## Flagged, not fixed (by design, per the answered questions)
- **Round trip only changes the message shown** - the facade still builds
  one one-way route. A real out-and-back pipeline (double the route once
  the destination is reached, or build a there-and-back `Route` upfront)
  is a flagged fast-follow, not built this pass.
- **OAuth stays a manual copy-paste step** - Connect opens real Google
  consent in a new tab; the authorization code still has to be copied
  from the redirect URL and pasted into the accordion. A real
  `/oauth/callback` route (auto-captures the code, no copy-paste) was
  explicitly deferred.
- No gender/stride input added to the UI - not asked for, and
  `IntakeRequest.gender` already defaults to `None` (unisex stride
  fallback) without it.
- The autocomplete dropdown's popup list didn't render visibly in
  automated screenshots even though the underlying choices were
  confirmed populated via the accessibility tree - looked like an
  automation/timing quirk of Gradio's combobox overlay, not a data bug;
  worth a real-browser eyeball check next session.
- `search_places` has no debounce beyond a blunt 0.3s per-field
  throttle (skips a call fired too soon rather than canceling/queuing) -
  fine for an MVP, matches `geocoder.py`'s own existing "swap in your own
  before real traffic" caveat about Nominatim's public demo server.

## How to run it
```bash
venv/bin/python3 -m pip install -q -r requirements.txt
venv/bin/python3 -m uvicorn services.fitbit_service:app --reload
```
Then open `http://127.0.0.1:8000/` - the UI and the webhook now share the
one process (fixes day4's in-memory-session-per-process gotcha as a side
effect of Q4's answer). Note: this session's venv had a stale shebang
(`venv/bin/pip`) pointing at the pre-move `Documents/WorldWalker` path
after the project folder was renamed to `Documents/projects/WorldWalker`
mid-session - use `venv/bin/python3 -m pip` instead, or recreate the venv.
